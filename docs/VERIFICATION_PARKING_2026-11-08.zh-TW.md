# 分組停車顯示回歸

日期：2026-11-08。線上雲端驗收發現：共用景點設定 A／B 分組停車後，選 B 組仍會在目前／下一站及時間軸顯示其他組的停車。下一站摘要又未顯示組名，容易選錯停車入口。

原因是停車集合只依安排行程的 `groupId` 過濾，未納入畫面選定群組；共用安排沒有 `groupId`，因此每組的停車都被列出。

本次在共用的停車集合選擇函式交集處理「安排所屬群組」與「目前檢視群組」，目前站、下一站及時間軸均使用相同選擇規則。共用停車維持各組可見；所有行程及旅程首頁仍列出各組，下一站在內容欄標示組名，保留原版緊湊的「停車」標籤。沒有修改資料格式、保存內容或 Firebase Rules。

## 驗證

- 新增三項回歸測試，涵蓋共用站分組篩選、行程群組與檢視群組交集、不存在／未設定群組、共用停車與無停車資料。
- `npm run check`：181 項單元、Rules 產生一致性與 production build 通過；依賴安全稽核 0 vulnerabilities。
- 全新本機 production preview 匯入兩筆安排、三個群組的合成資料。B 組下一站僅顯示 B 主備停車及備註；A 組目前站僅顯示 A 主備停車；未配置停車的 C 組不借用其他組資料。
- 所有行程清楚列出 A／B 組名；從 B 組切回旅程首頁，首頁仍保留全部組別的下一站停車，不受每日行程篩選影響。
- 390px 瀏覽器寬度實測，文件 clientWidth／scrollWidth 均為 375px（含瀏覽器捲軸差異），沒有水平溢出；檢查後已還原 viewport。

首輪單元測試曾指出把長組名放入 42px 標籤欄會破壞原有版面約定；已改將組名放進內容欄，原有測試未被刪除或放寬，完整重跑通過。
