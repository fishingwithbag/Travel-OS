# 升級雲端旅程儲存格式

新版每次把完整旅程保存為不可修改的版本，再原子切換 head 並刪除上一版本。Rules 會重新驗證全份行程、群組、停車、景點、租車、住宿及費用，拒絕直接局部刪除造成的孤立群組參照。一般保存只保留目前版本，不提供伺服器歷史回復功能；請持續下載完整備份。

這是 Firebase 儲存配置變更，旅程與 JSON 備份的 `schemaVersion` 仍為 1。IndexedDB 本機資料不需遷移。

## 維護者先更新

1. 保留目前的完整私人備份，通知旅伴更新網站，關閉開啟中的編輯表單。
2. 發布同一版本網站與 `firebase/database.rules.json`。設定精靈 Step 2 可複製此版本 Rules，維持原有 Spark，不需 Functions、Admin SDK 或計費升級。
3. 重新登入並執行 Step 5。診斷會送出目前的儲存格式標記；舊版 Rules 會拒絕，並提示回 Step 2 更新。這項診斷不是完整安全稽核。

更新 Rules 後，舊格式旅程仍可讀、可匯出，由擁有者管理成員；原位置禁止繼續編輯。不要用公開讀寫規則排除錯誤，也不要讓新版網站搭配舊版 Rules 長期運作。

## 擁有者逐趟操作

1. 開啟舊旅程，在「舊旅程需要升級儲存格式」按「下載備份並預覽升級」。此時尚未修改雲端資料。
2. 確認下載檔案已保存。這是私人完整備份，保留各類旅程資料，並另附 `migrationOriginalData` 保存未正規化的原始資料。不要公開分享這個檔案。
3. 檢查旅程版本與各類數量。若發現遺失群組，預覽會列出「待確認群組」與原 ID；原有行程、分組停車及預訂仍保留。原群組名稱無法推回，確認後可自行更名或移轉。
4. 勾選已保存備份及同意修復，再按「確認升級這趟旅程」。只有 owner 可以執行；editor/viewer 仍可閱讀，不能替擁有者確認。
5. 升級將完整資料寫至 `versions/{revision}`、設定 head、刪除舊 data，並保持成員權限。全部在一次原子更新完成；驗證失敗時整次不成立，原資料不會先被刪除。
6. 完成後可繼續編輯。若其他裝置已先升級或版本變更，請重新載入並重新下載備份，不要重用過期預覽。

其他不支援的資料損壞會阻止遷移，不能靠補回群組掩蓋。請保留原資料，勿手動清空資料庫。

## 回復與還原

發生問題時，使用「匯入備份」選擇升級前的完整備份，檢查預覽後匯入為**新的雲端旅程**。新旅程由目前登入者擁有；原旅程保留，不自動複製成員權限。請核對資料後再邀請成員。

不要把舊 data 路徑寫回新版旅程，也不要回退 Rules 為寬鬆規則。新版 Rules 會拒絕舊客戶端寫入舊 data；較早版本網站可能將新儲存格式視為不相容或空資料，請更新網站並重整，勿另建空白內容來覆蓋原 ID。

## 測試與範圍

測試直接使用正式 Rules，涵蓋 owner/editor/viewer、直接局部寫入、缺少與錯誤參照、原子刪舊版本、舊格式唯讀、owner 遷移、失敗無損、版本衝突、成員與備份還原。保存衝突由伺服器 revision 條件拒絕，不以用戶端先讀版本作為唯一保護。

本機瀏覽器透過隔離的 Emulator 及測試用身分 adapter 完成下載備份、預覽、確認升級與再次保存。這不代表已通過真實 Authentication、Spark 額度、大型旅程效能或多裝置雲端驗收；這些屬後續發布門檻。
