# 群組遺失與資料復原

正常刪除群組請使用「管理」的影響預覽與移轉流程。一次完整版本發布會一併更新行程、停車、租車、住宿、費用；停車內容衝突時拒絕覆蓋。多人變更以旅程版本檢查避免舊表單覆蓋。

## 遺失參照的處理

若備份或雲端資料仍有行程、停車或預訂指向已不存在的群組，Travel OS 會產生「待確認群組」，保留原 group ID 和所有關聯內容。原名稱已刪除時無法憑空還原；不猜測使用者屬於哪組，也不將不同群組併成所有人。

- 備份：匯入預覽明確顯示修復數量。取消時不寫入資料；確認後匯入含復原群組的旅程。原始備份檔案保持不變。
- 舊格式雲端旅程：維持唯讀，由 owner 下載備份、預覽遺失群組並確認升級後，原子寫入完整新版本；editor/viewer 不能代為遷移。詳見 [儲存格式升級指南](STORAGE_MIGRATION.zh-TW.md)。
- 新格式雲端旅程：異常參照會先提供復原預覽，owner/editor 確認後才保存。正常 Rules 寫入已禁止局部刪除造成孤立參照；此恢復入口保留給既有異常或管理者寫入的資料。
- viewer 可讀取預覽，無法保存。陌生人仍不能讀取旅程。復原只處理資料群組，不新增成員、不改權限。
- 修復後可透過群組「管理」更名，或預覽影響後移轉到另一群組。
- 其他格式錯誤、無效 ID、超過群組上限仍拒絕處理，不會以修復群組掩蓋其他損壞。

## 後端限制與驗收邊界

Firebase 的 `.validate` 不會驗證已刪除資料，單靠子節點驗證無法保護未變動的兄弟參照。正式 Rules 現以全新版本路徑重驗整份資料，並拒絕修改已發布版本；新 head、完整版本與清除舊版本必須原子完成。這取代早期僅有恢復預覽的限制。參考 [Firebase 官方 Rules 條件文件](https://firebase.google.com/docs/database/security/rules-conditions)。

正式 Rules 與多 SDK Emulator 已驗證；本機隔離瀏覽器完成遷移與保存。真實多帳號、Spark 與發布驗收仍需繼續處理。
