# 群組遺失與資料復原

正常刪除群組請使用「管理」的影響預覽與移轉流程。一次旅程交易會一併更新行程、停車、租車、住宿、費用；停車內容衝突時拒絕覆蓋。多人變更以旅程版本檢查避免舊表單覆蓋。

## 遺失參照的處理

若備份或雲端資料仍有行程、停車或預訂指向已不存在的群組，Travel OS 會產生「待確認群組」，保留原 group ID 和所有關聯內容。原名稱已刪除時無法憑空還原；不猜測使用者屬於哪組，也不將不同群組併成所有人。

- 備份：匯入預覽明確顯示修復數量。取消時不寫入資料；確認後匯入含復原群組的旅程。原始備份檔案保持不變。
- 雲端：先提供暫時的復原預覽及提示。需要 owner 或 editor 按「確認並保存群組修復」，才透過原有旅程交易保存。確認前一般編輯會提示先處理復原，避免無聲保存。
- viewer 可讀取預覽，無法保存。陌生人仍不能讀取旅程。復原只處理資料群組，不新增成員、不改權限。
- 修復後可透過群組「管理」更名，或預覽影響後移轉到另一群組。
- 其他格式錯誤、無效 ID、超過群組上限仍拒絕處理，不會以修復群組掩蓋其他損壞。

## 後端限制與驗收邊界

Firebase 的 `.validate` 規則在刪除時有特殊語意；請參閱 [Firebase 官方 Rules 條件文件](https://firebase.google.com/docs/database/security/rules-conditions)。本專案 Emulator 案例另外重現：已授權 editor 直接局部刪除 `groups/{id}` 並增加 revision 時，未變更的兄弟行程資料不會重新執行其參照驗證。

因此復原流程改善這類資料的可讀取性與修復能力，**沒有讓任意局部寫入取得嚴格的參照完整性保證**。完整 snapshot 正常寫入仍檢查參照；全域後端保證、真實多帳號復原及發布驗收仍需繼續處理。這項限制不涉及陌生人或 viewer 獲得寫入權限。
